## 1. Principles

### P1. 빠른 게임 진입, 낮은 진입 장벽
- 앱 실행부터 첫 윷 던지기까지 3탭 이내. 복잡한 튜토리얼 없이 직관적 UI로 누구나 즉시 플레이할 수 있어야 한다.
- 경쟁 앱(모두의 윷놀이, 한게임)의 공통 불만이 "매칭 대기"인 점을 감안, 매칭 시간 목표 15초 이내.

### P2. 공정한 경쟁, 투명한 시스템
- Glicko-2 레이팅 기반 매칭으로 실력 격차 최소화. 랜덤 시드는 서버에서 생성하여 클라이언트 조작 원천 차단.
- "확률 조작 의심"이라는 한게임류의 치명적 불만을 원천 해소. 윷 결과 확률 로그를 통계로 공개하는 것도 검토.

### P3. 수익화와 플레이 경험의 균형
- 광고는 게임 흐름을 끊지 않는 위치에만 배치. 보상형 광고 중심으로 유저 선택권 보장.
- "광고 과다"가 경쟁 앱 최대 불만인 점을 반면교사로, 과금 없이도 핵심 게임플레이를 온전히 즐길 수 있어야 한다.

### P4. 한국 전통 + 현대 캐주얼의 비주얼 조화
- 한지/나무 질감으로 전통미를 살리되, 밝고 둥근 캐릭터 말과 팝 컬러로 MZ세대 접근성 확보.
- "할아버지와 손자가 함께 즐기는 게임"이라는 윷놀이의 본질적 매력을 비주얼로 표현.

### P5. 서버 권위(Server-Authoritative) 게임 로직
- 모든 게임 상태(윷 결과, 말 이동, 잡기, 승리 판정)는 서버에서 계산하고 클라이언트는 렌더링만 담당.
- 치팅 방지, 분쟁 해소, 리플레이 기능의 기반이 되는 핵심 아키텍처 원칙.

## 2. Decision Drivers

### D1. 타임 투 마켓 (Time-to-Market)
- React Native + Expo 기반으로 iOS/Android 동시 개발. MVP를 3개월 내 출시하여 시장 반응을 빠르게 검증해야 한다.
- 윷놀이 게임 시장은 진입장벽이 낮으므로 선점보다 빠른 이터레이션이 중요.

### D2. 리텐션과 재방문율
- 윷놀이는 단판 게임 특성상 세션이 짧아 리텐션 확보가 핵심 과제.
- 시즌 티어, 리더보드, 친구 대전, 새로운 게임 모드 등으로 반복 방문 동기를 다층적으로 설계해야 한다.

### D3. 공정성 신뢰도
- 유저 신뢰가 무너지면 복구 불가. 서버 권위 로직 + 투명한 확률 시스템 + 이탈/어뷰징 패널티로 건전한 게임 생태계를 구축해야 한다.
- 경쟁 앱들의 "확률 조작", "비매너 유저" 불만을 차별화 포인트로 전환.

## 3. Viable Options

### Option A: MVP-First Incremental (권장)
> Colyseus + Firebase 기반, 1v1/2v2 핵심 모드 먼저 출시 후 점진적 확장

**Pros (bounded)**
- MVP 3개월 내 출시 가능 (Colyseus의 방 관리/매치메이킹 내장 활용)
- Firebase Auth/Firestore 무료 티어로 초기 서버 비용 최소화 (MAU 50K까지 무료)
- 유저 피드백 기반 우선순위 조정 가능 (시장 불확실성 대응)
- Colyseus TypeScript 생태계가 React Native와 자연스럽게 통합

**Cons (bounded)**
- Colyseus 단일 프로세스 한계로 동시 접속 5,000+ 시 스케일링 작업 필요
- Firebase Firestore의 실시간 쿼리 비용이 DAU 100K+ 에서 급증 가능
- MVP 단계에서 빠진 기능(시즌 시스템 등)이 초기 리텐션에 영향 줄 수 있음

### Option B: Full-Feature Launch
> 모든 게임 모드 + 시즌 시스템을 한번에 출시

**Pros (bounded)**
- 출시 시점에 완성도 높은 콘텐츠로 초기 리뷰/평점 확보에 유리
- 시즌 시스템이 출시일부터 작동하여 리텐션 장치 즉시 가동

**Cons (bounded)**
- 개발 기간 7~9개월 이상 예상 (팀 규모 3~4명 기준)
- 시장 검증 없이 대규모 투자 → 피벗 비용 극대화
- 기능 간 의존성으로 버그 표면적 증가, QA 부담 가중
- 게임 디자인 리스크를 사전에 해결해야 함

### Option C: Serverless-First (Firebase Cloud Functions 중심)
> Colyseus 대신 Firebase Cloud Functions + Realtime Database로 게임 서버 구현

**Pros (bounded)**
- 서버 인프라 관리 부담 제거, 오토스케일링 내장
- Firebase 생태계 통합 (Auth + Firestore + Functions + Hosting) 단순

**Cons (bounded)**
- Cloud Functions cold start (1~3초)가 실시간 게임에 치명적
- 턴 기반이라 해도 윷 던지기→결과→말 이동 사이클이 400ms 내 응답 필요
- 게임 상태 관리를 직접 구현해야 함 (Colyseus는 내장)
- WebSocket 미지원으로 Realtime Database polling 기반 → 지연 + 비용 증가
- **결론: 실시간 게임 요구사항에 부적합하여 무효화**

> **Option C 무효화 근거**: 윷놀이는 턴 기반이지만, 윷 던지기 애니메이션 동기화, 말 이동 실시간 반영, 잡기 이벤트 즉시 전파 등 준실시간(sub-second) 통신이 필수. Cloud Functions의 cold start와 HTTP 기반 통신은 이 요구를 충족하지 못하며, WebSocket 기반 Colyseus가 명확히 우위.

## A. 게임 개요

### 컨셉
**"쉽고, 빠르고, 공정한 모바일 윷놀이"**

전통 윷놀이의 전략성과 운의 조화를 현대적 모바일 UX로 재해석. 캐주얼 유저는 빠른 매칭으로 즉시 즐기고, 경쟁 유저는 시즌 티어와 리더보드로 성장 동기를 얻는 이중 구조.

### 타겟 유저

| 세그먼트 | 연령대 | 특성 | 핵심 니즈 |
|---------|--------|------|----------|
| 캐주얼 플레이어 | 10~60대 | 가족/친구와 가볍게 즐김 | 빠른 매칭, 쉬운 조작, 친구 초대 |
| 경쟁 플레이어 | 20~40대 | 랭킹/티어에 동기부여 | 공정한 매칭, 리더보드, 시즌 보상 |
| 소셜 플레이어 | 20~30대 | 친구와 함께하는 경험 중시 | 2v2 팀전, 채팅, 이모티콘 |
| 향수 플레이어 | 40~60대 | 명절/추억의 윷놀이 | 전통적 비주얼, 심플한 UI |

### 차별점

1. **스킬 게이지 시스템**: 골프 게임 스타일의 타이밍 게이지로 윷 결과에 실력 요소 추가 → 운 70% + 실력 30%의 하이브리드 (업계 최초)
2. **서버 권위 공정성**: 윷 결과 서버 생성 + 확률 통계 투명 공개 → "조작 의심" 원천 차단
3. **스마트 광고**: 게임 중 광고 없음. 게임 종료 후 + 보상형만 사용 → "광고 과다" 불만 해소
4. **스피드 모드**: 10초 턴, 말 2개로 빠른 게임. 전통 윷놀이에 현대적 재미 추가
5. **비주얼 퀄리티**: Rive 기반 윷 던지기 애니메이션 + react-native-skia 보드 렌더링으로 경쟁 앱 대비 압도적 비주얼

### 레퍼런스 앱

| 앱 | 참고 포인트 |
|----|-----------|
| **모두의 마블** | 보드게임 앱 성공 공식 (소셜 바이럴, 캐릭터 IP, 방 만들기 UX, 파티 게임 포지셔닝) |
| **모두의 윷놀이** | 직접 경쟁 앱. 기본 기능 벤치마크 + 불만사항(광고 과다) 반면교사 |
| **한게임 윷놀이** | 배팅/과금 모델 참고. "확률 조작" 불만을 차별화 기회로 전환 |
| **루미큐브 앱** | 매칭 + 방 만들기 이중 구조, 시즌 티어제 |

### 타겟 시장 & 마케팅 전략

#### 한국 시장

| 시나리오 | 타겟 | 마케팅 채널 |

| **친구 모임/MT** | 10~30대 | 대학생/직장인 타겟 바이럴, 단체 플레이 숏폼 콘텐츠 |

### UGC (User Generated Content) 마케팅 전략

> **컨셉**: 유저가 게임 플레이 영상/숏폼을 SNS에 올려서 자연 유입을 만드는 바이럴 구조. 인앱 마켓이 아닌, **게임 자체가 콘텐츠가 되는** 설계.

#### "콘텐츠가 되는 게임" 설계 원칙
1. **명장면 자동 감지**: 연속 잡기, 대역전, 모 연발 등 하이라이트 순간을 서버에서 감지
2. **원터치 클립 내보내기**: 명장면을 15초 숏폼 영상/GIF로 자동 생성 → 틱톡/인스타/유튜브 쇼츠에 바로 공유
3. **시각적 임팩트**: 윷/모 시 화려한 이펙트, 잡기 시 연출 등이 "보는 재미"를 만들어야 함
4. **워터마크 + 앱 링크**: 내보낸 영상에 자연스러운 게임 로고 + 다운로드 링크 삽입

#### UGC 바이럴 채널

| 채널 | 콘텐츠 유형 | 유입 경로 |
|------|-----------|----------|
| **틱톡/릴스/쇼츠** | "모 3연발 ㅋㅋ", 가족 대전 리액션, 커플 대결, 대역전 하이라이트 | 영상 내 다운로드 링크 |
| **K-pop 예능/V-live** | 아이돌이 설날 특집으로 윷놀이 하는 장면 → 팬덤이 자발적 공유 | 팬 커뮤니티 바이럴 |
| **유튜브/트위치** | 스트리머 플레이 영상, "윷놀이 고수 vs 초보" 같은 기획 콘텐츠 | 유튜브 검색 유입 |
| **카카오톡** | 친구 초대 결과 공유 ("나 4연승 중"), 명장면 GIF 전송 | 딥링크 유입 |

#### 콘텐츠 유도 장치
- **공유 보상**: 영상 공유 시 인앱 보상 (이모티콘 1시간 시용, 방 만들기 +1회 등)
- **해시태그 챌린지**: 시즌별 #윷놀이챌린지 운영 (예: "모 3번 연속 나온 사람?", "가족 4인 대전 찍어봐")
- **리플레이 시스템**: 게임 종료 후 "이번 판 명장면" 자동 제안 → 탭 한 번으로 공유

## B. 게임 모드

### B0. 게이지 모드 선택 (모든 대전 모드 공통) - MVP
- **클래식 모드**: 순수 운 기반. 게이지 없이 탭 한 번으로 던지기. 전통 윷놀이 그대로.
- **스킬 모드**: 타이밍 게이지 적용. 잘 맞추면 윷/모 확률 미세 보정(+2%p).
- **매칭 분리**: 클래식 ↔ 스킬 간 매칭 큐 분리 (같은 모드끼리만 매칭)
- **기본값**: 클래식 모드 (신규 유저 진입장벽 최소화)
- **방 만들기**: 방장이 클래식/스킬 선택

### B1. 개인전 (1v1) - MVP
- **설명**: 1:1 대전. 가장 기본적인 경쟁 모드.
- **매칭**: 빠른 매칭 (Glicko-2 레이팅 기반) 또는 방 만들기/참여
- **게이지**: 클래식 또는 스킬 모드 선택
- **말 개수**: 유저당 4개
- **턴 시간**: 30초 (윷 던지기 + 말 선택)
- **승리 조건**: 4개 말 모두 골인

### B2. 팀전 (2v2) - MVP
- **설명**: 2명이 한 팀. 팀원과 번갈아 턴 진행.
- **팀 구성**: 랜덤 매칭 또는 친구 초대로 팀 구성
- **말 개수**: 각자 말 **2개씩** (팀당 총 4개, 각자 자기 말만 조작)
- **턴 순서**: 1팀A → 2팀A → 1팀B → 2팀B (교차)
- **말풍선 메시지**: 프리셋 4종 방 전체 브로드캐스트
- **승리 조건**: 팀의 4개 말 모두 골인 (내 말 2개 + 팀원 말 2개)

### B3. 스피드 모드 (Speed Mode) - Phase 2
- **설명**: 턴 시간 10초로 단축된 긴장감 높은 변형 모드.
- **특수 규칙**:
  - 턴 시간 10초 (시간 초과 시 자동으로 가장 앞의 말 이동)
  - 윷/모 나와도 추가 턴 없음 (한 번에 끝)
  - 말 2개만 사용 (빠른 게임 진행, 판당 3~5분)
- **매칭**: 별도 큐, 레이팅 공유하되 모드별 보정값 적용
- **목적**: 짧은 세션 유저 타겟, 출퇴근 시간 등 틈새 시간 활용

### B4. AI 대전 (연습/오프라인) - MVP
- **설명**: AI 상대 연습 모드. 네트워크 불필요.
- **AI 난이도**: 3단계
  - **쉬움**: 랜덤 행동 (초보자 학습용)
  - **보통**: 간단한 휴리스틱 (잡기 우선, 업기 고려)
  - **어려움**: Minimax + 확률 계산 (최적 말 선택, 지름길 활용)
- **오프라인 지원**: 게임 로직을 클라이언트에도 탑재 (AI 전용)
- **목적**: 신규 유저 온보딩, 네트워크 불안정 시 대안, 규칙 학습

## C. 핵심 게임플레이

### C1. 윷놀이 기본 규칙

#### 윷 던지기 결과

| 이름 | 이동 칸수 | 기본 확률 (전통) | 서버 기본 확률 | 추가 턴 |
|------|----------|----------------|---------------|---------|
| 도 (Do) | 1칸 | ~25% | 25% | X |
| 개 (Gae) | 2칸 | ~31.25% | 31% | X |
| 걸 (Geol) | 3칸 | ~25% | 25% | X |
| 윷 (Yut) | 4칸 | ~12.5% | 13% | O |
| 모 (Mo) | 5칸 | ~6.25% | 6% | O |
| 백도 (Backdo) | -1칸 | 특수 (윷짝 1개만 뒤집힘) | 별도 판정 | X |

> **확률 산정 근거**: 전통 윷의 물리적 확률(4개 윷짝의 엎어짐/뒤집힘 조합)을 기반으로 서버에서 가중 랜덤 적용. 윷짝 개별 시뮬레이션이 아닌 결과 직접 샘플링 방식.

#### 스킬 게이지 시스템 (Skill Gauge)

> **컨셉**: 골프 게임의 파워 게이지와 유사. 윷을 던지기 전에 타이밍 게이지를 정확히 맞추면 "좋은 결과"가 나올 확률이 올라가는 스킬 요소를 추가.

**게이지 동작 방식**:
```
[게이지 바: ◀━━━━━━━●━━━━━━━▶]
         BAD    GOOD   PERFECT   GOOD    BAD
```

1. 턴 시작 시 게이지 바가 좌우로 왕복 이동 (속도: 1.5~2초 주기)
2. 유저가 "던지기" 버튼 탭 → 게이지 정지
3. 게이지 정지 위치에 따라 결과 확률 보정:

| 게이지 영역 | 판정 | 확률 보정 효과 |
|------------|------|--------------|
| PERFECT (중앙 10%) | 완벽 | 윷/모 확률 +2%p, 도 확률 -2%p |
| GOOD (중앙 30%) | 좋음 | 윷/모 확률 +1%p, 도 확률 -1%p |
| NORMAL (중앙 60%) | 보통 | 기본 확률 그대로 |
| BAD (양쪽 끝 20%) | 나쁨 | 도 확률 +2%p, 윷/모 확률 -1%p |

**설계 의도**:
- 순수 운 게임 → **운 90% + 실력 10%** 미세 보정 하이브리드로 전환 (보정폭 +2%p로 운의 재미 유지)
- 경쟁 앱(모두의 윷놀이, 한게임)과의 **핵심 차별점**
- 골프/볼링 게임처럼 "잘 던졌다!"는 성취감 제공
- 모두의 마블의 주사위 던지기보다 한 단계 발전된 인터랙션

**주의사항**:
- 확률 보정은 미세하게 유지 (게임의 운 요소를 완전히 제거하지 않음)
- 게이지 속도는 레이팅에 따라 변하지 않음 (공정성)
- AI 대전에서도 AI가 게이지를 시뮬레이션 (난이도별 정확도 차등)
- 서버에서 최종 확률 계산 후 결과 생성 (클라이언트 조작 불가)

#### 말 이동 규칙
- **보드 구조**: 전통 윷판 (외곽 20칸 + 대각선 지름길)
- **출발**: 출발점에서 시계 반대 방향으로 이동
- **지름길**: 꼭짓점(모서리 칸)에 정확히 도착 시 대각선 지름길 선택 가능
  - 우측 상단 모서리 → 중앙 경유 좌측 하단 코스
  - 좌측 상단 모서리 → 중앙 경유 우측 하단 코스
  - 중앙 교차점에서 추가 분기 가능
- **골인**: 출발점을 지나거나 정확히 도착하면 골인 (남은 칸수보다 크게 나와도 골인 처리)

#### 잡기 (Catch)
- 상대 말이 있는 칸에 내 말이 도착하면 상대 말을 출발점으로 되돌림
- 잡기 성공 시 추가 턴 1회 획득
- 잡기 + 윷/모 추가 턴은 누적 (예: 모로 잡기 → 추가 턴 2회)

#### 업기 (Stack)
- 같은 칸에 내 말이 2개 이상 있으면 함께 이동 (업기)
- 업힌 말은 한 번에 같이 잡힐 수 있음 (고위험 고보상)
- 업힌 상태에서 일부 말만 분리 이동 불가 (전통 규칙 준수)

#### 지름길 (Shortcut)
- 모서리 칸 정확 도착 시 지름길 진입 선택권 부여 (UI에서 팝업)
- 지름길 미선택 시 외곽 경로 유지
- 중앙 교차점 도착 시에도 경로 선택 가능

### C2. 턴 시스템

```
[턴 시작] → [윷 던지기 대기: 5초] → [윷 애니메이션: 1~2초] 
→ [결과 표시] → [말 선택 대기: 25초] → [말 이동 애니메이션: 1초]
→ [추가 턴 여부 확인] → [턴 종료 / 추가 턴 시작]
```

- **턴 총 시간**: 30초 (윷 던지기 5초 + 말 선택 25초)
- **시간 초과 처리**:
  - 윷 던지기 미실행: 서버가 자동 던지기 실행
  - 말 미선택: 가장 뒤에 있는 말 자동 이동
- **연속 시간 초과 패널티**: 3턴 연속 시간 초과 시 기권 패배 처리
- **추가 턴**: 윷(4칸), 모(5칸), 잡기 성공 시 추가 턴 부여
  - 추가 턴은 큐에 누적 (예: 모 → 윷 → 잡기 = 3회 추가 턴)
  - 모든 추가 턴에서 개별 윷 던지기 수행

### C3. 승리 조건
- **기본**: 자신의 (팀의) 말 4개를 모두 골인시키면 승리
- **기권승**: 상대가 기권하거나 3턴 연속 시간 초과 시
- **연결 끊김**: 30초 내 재접속하지 않으면 기권 패배 처리
- **무승부**: 없음 (윷놀이 특성상 반드시 승패 결정)

## D. 시스템 설계

### D1. 인증/로그인 플로우

```
[앱 실행] → [스플래시 + 자동 로그인 시도]
  ├─ 기존 토큰 유효 → [메인 로비]
  └─ 토큰 없음/만료 → [로그인 화면]
       ├─ [카카오 로그인] → Kakao SDK → 서버 → Firebase Custom Token
       ├─ [구글 로그인] → Google Sign-In → Firebase Auth
       └─ [Apple 로그인] → Apple Sign-In → Firebase Auth
```

**상세 플로우**:
1. **카카오 로그인**: `@react-native-seoul/kakao-login`으로 카카오 토큰 획득 → 백엔드에서 카카오 유저 정보 검증 → Firebase Admin SDK로 Custom Token 발급 → 클라이언트에서 `signInWithCustomToken()`
2. **구글 로그인**: `@react-native-google-signin` → Firebase Auth `signInWithCredential()`
3. **Apple 로그인**: `@invertase/react-native-apple-authentication` → Firebase Auth `signInWithCredential()`

**프로필 데이터**:
- 닉네임 (2~10자, 중복 불가, 비속어 필터)
- 프로필 이미지 (소셜 계정 기본 or 기본 아바타 6종)
- 레이팅 점수, 시즌 티어, 전적

### D2. 매칭 시스템

#### 빠른 매칭 (Quick Match)

```
[매칭 요청] → [Redis 매칭 큐 등록]
  → [Glicko-2 레이팅 +-200 범위 내 상대 검색]
  → [5초 내 미매칭 시 범위 +-400으로 확대]
  → [10초 내 미매칭 시 범위 +-800으로 확대]
  → [15초 내 미매칭 시 전체 풀에서 매칭]
  → [매칭 성공] → [Colyseus Room 생성] → [게임 시작]
```

- **모드 선택**: 1v1 / 2v2 각각 별도 큐
- **2v2 매칭**: 솔로 큐 (4명 개별 매칭) + 듀오 큐 (2+2 팀 매칭)
- **매칭 취소**: 큐 대기 중 언제든 취소 가능

#### 방 만들기 (Custom Room)

- **방 생성**: 6자리 숫자 코드 자동 생성
- **방 설정**:
  - 모드: 1v1 / 2v2
  - 턴 시간: 15초 / 30초 / 60초
  - 비밀번호 (선택)
- **방 참여**: 코드 입력 또는 초대 링크
- **방 제한**: 무제한 무료 (수익화는 광고 제거/스킨에 집중, 가족·커플·친구 모임 시나리오를 방해하지 않음)
- **방 유효 시간**: 생성 후 5분 내 미시작 시 자동 소멸

#### 친구 초대 (Friend Invite)

- **딥링크**: `yut://room/{roomCode}` (앱 설치 시) / Universal Link (미설치 시 스토어 이동)
- **카카오 공유**: 카카오톡 메시지 템플릿으로 방 코드 + 딥링크 전송
- **일반 공유**: 시스템 공유 시트 (URL + 방 코드 텍스트)

### D3. 채팅 시스템

#### 게임 중 말풍선 메시지 (In-Game)
- **구현**: Colyseus Room 메시지로 처리 (별도 채팅 서버 불필요)
- **방식**: 방 전체에 브로드캐스트. 보낸 유저의 캐릭터 위에 **말풍선**으로 표시.
- **프리셋 4종**:
  1. "미안해요"
  2. "잘했어요"
  3. "빨리 주세요"
  4. "왔어요"
- **UI**: 화면 하단에 4개 버튼 → 탭 시 즉시 말풍선 표시 (2초간 노출 후 페이드아웃)
- **제한**: 연속 메시지 3초 쿨다운 (스팸 방지)
- **비속어 리스크 없음**: 프리셋만 사용하므로 별도 필터링 불필요

#### 로비 채팅 - 불필요
> 로비 채팅은 운영 비용 대비 가치가 낮아 제외. 게임 내 프리셋 메시지로 소통 충분.

### D4. 리더보드 (승패 기반)

#### 심플 승패 시스템

> 복잡한 레이팅/티어 시스템 대신, **승수(총 승리 횟수)** 기반의 직관적 리더보드.

- **핵심 지표**: 총 승수 (월간)
- **매칭**: Glicko-2 레이팅은 내부적으로만 사용 (매칭 품질 확보용). 유저에게는 노출하지 않음.
- **초기화**: **매월 1일** 리더보드 리셋 → 매달 새로운 경쟁
- **월간 리더보드 보상**: Top 유저에게 한정 캐릭터 해금 (플레이 동기)

#### 리더보드 종류

| 리더보드 | 기준 | 표시 정보 |
|---------|------|----------|
| **글로벌 리더보드** | 월간 승수 Top 100 | 닉네임, 승수, 승률, 캐릭터 |
| **친구 리더보드** | 카카오 친구 중 월간 승수 순위 | 닉네임, 승수, 승률 |

- **프로필 통계**: 총 전적, 승률, 연승 기록, 월간 승수
- **업데이트 주기**: 실시간 (게임 종료 즉시)

### D5. 이탈 방지/패널티 시스템

| 행위 | 감지 방법 | 패널티 |

### E1. 광고 전략

|------|------|------|
| 주간 이용권 | 2,900원/주 | 광고 전체 제거 + 추가 캐릭터 8종 해금 |
| 월간 이용권 | 7,900원/월 | 광고 전체 제거 + 추가 캐릭터 8종 해금 |

**구독 = 광고 제거 + 캐릭터**. 단순 명확.

**해지 시**: 광고 복원 + 추가 캐릭터 잠금 (기본 4종은 유지)

### E3. 평생 이용권

| 상품 | 가격 | 혜택 |
|------|------|------|
| 평생 이용권 | 29,900원 | 영구 광고 제거 |

- 월간 구독 약 3.8개월분 가격으로 책정 → 장기 유저에게 합리적 선택
- RevenueCat으로 구현, Non-consumable 상품으로 등록

### E4. 캐릭터 시스템

> **컨셉**: 심플하게. 기본 캐릭터 + 구독자 추가 캐릭터.

- **무료 유저**: 기본 캐릭터 **4종** (각 플레이어 색상별 1종)
- **구독자**: 추가 캐릭터 **8종** 해금 (동물, 전통 테마 등)
- **캐릭터 = 말 외형**: 캐릭터 선택 시 게임 내 말 모양이 변경됨
- **구독 해지 시**: 추가 8종 잠금, 기본 4종으로 복원
- **Pay-to-Win 없음**: 캐릭터는 순수 외형. 게임 성능 차이 없음.

**수익 모델 요약 다이어그램**:
```
[무료 유저]
  ├─ 보상형 광고 (게임 종료 후)
  ├─ 배너 광고 (로비)
  ├─ 방 만들기 무제한
  ├─ 모든 게임 모드 이용 가능
  └─ 기본 캐릭터 4종

[구독자 (주간/월간)]
  ├─ 광고 전체 제거
  └─ 추가 캐릭터 8종 해금

[평생 이용권]
  └─ 광고 전체 제거 (영구)
```

### F3. 애니메이션 계획

#### 핵심 애니메이션 (P0 - Rive)

**윷 던지기 애니메이션**:
- Rive State Machine 기반, 결과별 3~5가지 변형
- 구조: `[손 동작] → [윷짝 공중 회전] → [착지 바운스] → [결과 정렬]`
- 각 결과(도/개/걸/윷/모)별 윷짝 최종 배치가 다름
- 유저 입력: 화면 스와이프/탭으로 던지기 트리거 → Rive State Machine input
- 소요 시간: 1.5~2초
- 파일 크기 목표: .riv 파일 200KB 이내

**말 이동 애니메이션**:
- react-native-reanimated 기반 (Rive 불필요)
- 홉(hop) 포물선: 칸 이동마다 포물선 궤적
- 스쿼시 & 스트레치: 착지 시 말이 눌렸다 복원
- 다칸 이동: 중간 경유칸을 순차적으로 홉 (1칸당 200ms)
- 업기: 말 위에 말이 올라타는 스택 애니메이션

#### 부가 애니메이션 (P1 - Lottie)

**잡기 이펙트**:
- 충돌 지점에서 별/먼지 파티클 폭발 (0.5초)
- 잡힌 말이 출발점으로 날아가는 궤적
- 햅틱 피드백: `Haptics.impactAsync(ImpactFeedbackStyle.Heavy)`

**승리/패배**:
- 승리: 화면 상단에서 컨페티 쏟아짐 + 골든 글로우 보드 + 승리 사운드
- 패배: 화면 살짝 어두워짐 + 위로 메시지

**턴 전환**:
- "내 턴!" 텍스트 바운스 인 → 페이드 아웃
- 상대 턴 시 보드 테두리 색상 변경 (상대 색으로)

#### 네트워크 복원력

- **Heartbeat**: 2초 간격 ping/pong
- **State Sync**: Colyseus의 자동 delta 동기화 (변경분만 전송)
- **재접속**: Room의 `allowReconnection(client, 30)` 활용
- **지연 보상**: 클라이언트 예측 없음 (턴 기반이므로 불필요), 서버 응답 후 애니메이션 재생
- **오프라인 감지**: NetInfo + Colyseus disconnect 이벤트 → 재접속 UI 표시

## ADR

### Decision: MVP-First Incremental 접근법 (Option A) 채택

**Drivers**:
1. 3개월 내 시장 검증 필요 (Time-to-Market)
2. 유저 피드백 기반 이터레이션이 윷놀이 게임 시장에서 더 효과적
3. 초기 인프라 비용 최소화 (Firebase 무료 티어 + 단일 Colyseus 서버)

**Alternatives Considered**:
- **Option B (Full-Feature Launch)**: 7~9개월 개발 기간, 시장 검증 전 대규모 투자 리스크. 기각 사유: 윷놀이 앱 시장의 불확실성 대비 투자 규모 과다.
- **Option C (Serverless-First)**: Cloud Functions cold start가 실시간 게임에 부적합. 기각 사유: 기술적 한계로 핵심 요구사항(준실시간 통신) 미충족.

**Why Chosen**:
- Colyseus의 내장 매치메이킹/방 관리가 MVP 개발 속도를 극대화
- Firebase 생태계로 인증/DB/알림을 빠르게 구축, 이후 필요시 마이그레이션 가능
- 핵심 게임플레이(1v1, 2v2, AI)만으로도 경쟁 앱 대비 차별점(공정성, 비주얼) 검증 가능

**Consequences**:
- (+) 빠른 출시로 시장 피드백 조기 수집
- (+) 단계적 투자로 리스크 분산
- (-) Phase 1 출시 시 콘텐츠 부족으로 초기 리텐션 도전
- (-) Colyseus 스케일링 한계에 도달하면 서버 아키텍처 재작업 필요

**Follow-ups**:
- Phase 1 출시 후 DAU 1K 도달 시점에 서버 스케일링 계획 수립
- Phase 2 시작 전 유저 설문으로 스피드 모드 우선순위 확인
- Firestore 비용이 월 $100 초과 시 PostgreSQL 마이그레이션 검토 시작
- 시즌 1 종료 후 티어 분포 분석하여 레이팅 구간 조정
